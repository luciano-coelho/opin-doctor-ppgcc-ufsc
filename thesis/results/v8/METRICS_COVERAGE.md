# v8 Metrics Coverage

Maps every metric in v7's `Consolidated_Metrics_Report_FINAL.md` (computed by
`thesis/scripts/compute_v7_report_data.py` from `thesis/results/v7/report_data_v7.json`)
to its v8 data source, plus the new metrics v8 adds. Written during the
2026-10-21 light flow check (Decision — see `DECISIONS.md`): that check ran
`opin_flow.py`/`campaign_client_runner.py` for real, under Python 3.9 in an
`amazonlinux:2023` container with the campaign's own `--memory=8g --cpus=2`
limits, for all three crypto profiles, against the local MockOPIN stack. The
"v8 data source" and "status" columns below are not guesses: most were
cross-checked against the check's own real output, reported inline.

**v8 campaign folder structure** (Decision 53, `campaign_run.py` docstring):

```
v8/latency/experiment{1,2,3} - {Classic,PQC,Hybrid}/{server}/{scenario}/
  runs/run{NN}.json           (window, server, client, instance_type, result)
  runs/run{NN}.calls.jsonl    (per-call record: endpoint, request_bytes,
                               response_bytes, jwt_sizes, jwk_sizes, latency_ms)
  server/run{NN}_gateway.log, run{NN}_cpu.jsonl, run{NN}.pcap.gz
  client/run{NN}_cpu.jsonl, run{NN}_ping.json, run{NN}.pcap.gz
  median_metrics.json, report.md   (local post-processing -- consolidate_v8.py)

v8/size/experiment{1,2,3} - {Classic,PQC,Hybrid}/{server}/
  median_metrics.json, report.md   (derived from v8/latency's own runs, Decision 55/58)
```

## mTLS handshake

| Metric | Definition | v8 data source | Status | Observation |
|---|---|---|---|---|
| mTLS handshake: bytes (P50) | Same as term_handshake above, reported standalone | same as term_handshake | **covered (corrected 2026-10-22)** | Same real source and real numbers as term_handshake above. The cross-run drift against v7 (classic +1.17%, hybrid +5.52%) was investigated further (DECISIONS.md) and is NOT a cert-chain change (every cert confirmed byte-identical to v7 on disk) -- it's a real measurement-boundary artifact in `mock_mtls/main.go`'s own `connStateHandshakeLogger`: the byte counter is read at `ConnState -> StateActive`, which Go's HTTP server reaches strictly after the connection's FIRST REAL REQUEST has already started arriving (TLS 1.3 lets the client pipeline its first request right after its own Finished, with no extra round trip) -- confirmed via a real raw packet capture, byte for byte: 19,011 B = ClientHello(1,881) + server flight(7,240) + a server write immediately after it (2,162, consistent with a TLS 1.3 NewSessionTicket) + client flight(7,240) + the first request's own first 488 bytes(260+228), already counted before the logger reads the field. Same code as v7, so v7's own numbers carry the identical artifact -- the residual drift is which specific first-request content (JWT/JWK sizes differ per pool) happens to leak in, not a design change. Not something this generator can or should "fix" by itself (see DECISIONS.md for the open question on whether `main.go` itself should be corrected). |
| mTLS handshake: duration (ms) | Per-connection handshake time -- the "mTLS handshake" leg of v7's own flow-time decomposition (Section 4) | `server/run{NN}_gateway.log` -- same "mTLS handshake complete" lines, field `handshakeDurationMs` | **covered (new finding, 2026-10-22)** | Logged on the exact same line as `mtlsHandshakeBytes` (confirmed live: `"handshakeDurationMs":1`, same event) -- not something that needs separate instrumentation. `consolidate_v8.py` does not parse this yet (out of this turn's narrow scope, which was specifically the handshake-BYTES term); the flow-time-decomposition row below still only needs its "server processing" leg, not this one. |
| ClientHello: size (bytes) | The ClientHello message's own total size | `client/run{NN}.pcap.gz`, TLS record header's own length field (`payload[3:5]`, `pilot_acceptance.py`'s `find_first_clienthello()`) | **covered (2026-10-22 investigation)** | Verified exactly at the REAL campaign snaplen (128 bytes): classic 341, pqc 1,784, hybrid 1,881 -- exact matches to the v7 reference fixture, real local captures. No reassembly needed even though the full ClientHello spans more than one real TCP segment on the wire for pqc/hybrid: the record's own declared length sits in the first 5 bytes, always inside the first captured segment. `pilot_acceptance.py` already had this (Criterion 2); it just needed its own SNI-gating bug fixed (see the next row and DECISIONS.md). |
| ClientHello: SNI | The `server_name` extension's value ("mtls") | `client/run{NN}.pcap.gz` | **not covered at the real snaplen (128)** | SNI sits at TLS-payload offset ~97 (measured directly); at snaplen=128 only ~62 bytes of payload are actually captured (header overhead measured at 66 bytes for a real frame with TCP timestamp options), so SNI is never recoverable there -- confirmed both ways: `None` at snaplen=128, `'mtls'` recovered exactly at snaplen=256 against the same connection class. Minimum snaplen measured: ~168 bytes; recommended with margin: 256 (real measured cost of going from 128: +47.6% pcap size for one connection's capture, 44,774 -> 66,098 bytes). Snaplen NOT changed (Luciano's own call, DECISIONS.md) -- `pilot_acceptance.py`'s Criterion 2 no longer gates on SNI (it used to, which would have failed every real pilot execution unconditionally), only reports it when present. |

## Summary

- **Fully covered, exact or near-exact match confirmed against v7's own numbers using real data:** term_jwt, term_jwk, term_pki, term_handshake (and therefore OPINsize's own complete total), N_mTLS, N_JWT, N_JWK, N_PKI, call count (42), average JWT, JWK_PK_size, average PKI_bytes, bytes-per-participant. OPINsize itself: classic +0.47%, pqc exact, hybrid +1.70% against v7 -- all within `pilot_acceptance.py`'s own ±3% tolerance.
- **Corrected this turn (2026-10-22), after being wrong last turn:** term_handshake/mTLS-handshake-bytes/OPINsize were marked "not covered, needs a pcap extractor" -- investigation found the real source (`server/run{NN}_gateway.log`'s own `mtlsHandshakeBytes`) was already collected and already pulled; only a parser was missing, now written (`consolidate_v8.py`'s `term_handshake()`/`client_facing_handshakes()`, reusing `campaign_run.py`'s own log-parsing/channel-disambiguation code). N_mTLS's planned `pool_label`-based source was also found wrong when checked against real data (4, not 6) and replaced with the gateway-log-derived count.
- **Covered, backed by existing, already-wired instrumentation, not independently re-verified this turn:** client certificate DER bytes (static file read), latency per endpoint, T_fluxo, RTT, packet loss (upper bound), CPU/steal/memory.
- **Resolved 2026-10-22 (second follow-up turn):** flow-time decomposition's server-processing leg (`opin_processing_ms`, same root pattern as term_handshake -- already logged, already collected, already pulled, only unparsed) and ClientHello's own SIZE (same pattern, already handled by existing `pilot_acceptance.py` code, exact at the real snaplen). ClientHello's own SNI is NOT covered at the real campaign snaplen (128) -- confirmed genuinely unrecoverable there, not a parser gap; `pilot_acceptance.py`'s Criterion 2 had a latent bug gating on it anyway (fixed).
- **Investigated, found NOT to be a cert-chain/design change (open question, Luciano's own call):** the handshake-bytes cross-run drift against v7 (classic +1.17%, hybrid +5.52%) is a real measurement-boundary artifact in `mock_mtls/main.go`'s own handshake-byte counter (reads the counter after the connection's first real request has already started arriving) -- same code as v7, so not a new discrepancy v8 introduced, but not something this generator can fix either. See DECISIONS.md for the full trace.
- **New, to be computed at consolidation time, not a raw field:** bootstrap CI of the median.

A note on the "42 requests" vs "28 total_requests" figures, both real, both from v7, neither a mistake: v7 has two separate pipelines over the same underlying flow -- the *latency* experiment (`thesis/results/v7/latency/`, same `call_count=42` field this check reproduced) and the *size* experiment (`thesis/results/v7/size/`, which reports a different, narrower `total_requests=28`, counting requests at the level the byte/size instrumentation groups them, not every individual HTTP call). v8's `campaign_run.py` currently only builds the `v8/latency/` tree (Decision 53's docstring); the `v8/size/` tree is planned (Decision 55/58) to be *derived* from `v8/latency/`'s own runs, not collected separately -- so this check, which exercises the latency-style tooling, is measuring the right thing for what v8 currently builds.
